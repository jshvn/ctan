# What the pipeline could cut, 2026-08-26

Scope: `main` at 4d16ac1 plus this branch. Every task, flag, file and dashboard rule was
asked the same three questions: what breaks if it goes, how bad is that, and how soon would
we know. "We know" always means the same channel, one failed-run email, because that is the
only alerting the repo has and the only one it wants.

Measured for this review, against the CTAN master on 2026-08-26 with the tlpdb staged on
2026-08-25: 14,872 containers named yesterday, 14,873 upstream today, 0 gone, 1 new. The live
run 32941682244 emitted zero `delete:` lines. Revision bumps overwrite a container in place
under the same unversioned name, so churn creates no stale keys; only a package removal does.

Decisions so far: 4 and 5 applied (196f082, d9d6a02); 2, 3 and 6 kept, see "Kept by
decision"; 1 reworked below into a proposal that keeps the page.

## Findings

### 1. `page`: keep the page, drop the renderer

The page exists so search engines can find the mirror URL. That needs a page at `/` with
the URL, a title and a description in it, and an inbound link (the README on GitHub already
is one). It does not need to be the README.

The machinery today renders the README because a landing page that duplicated it would
drift. But the page's job is a signpost: what this is, the `tlmgr` URL, a link to the repo
for the rest. A signpost does not duplicate the README; it is a different, shorter document.
Once that is accepted, the whole renderer goes:

- `site/index.html` is checked in, hand-written, about thirty lines. `site/template.html`,
  the `.gitignore` line, `PAGE`, the `curl` to `api.github.com/markdown/raw`, the three-part
  `sed`, `body.html`, the `grep markdown-heading` render check, the `GITHUB_TOKEN` line in
  `sync.yml` and the rate-limit and render-check gotchas in CLAUDE.md all go. The endpoint
  list loses its fifth entry.
- `page` becomes one command, the existing `aws s3 cp` with `--cache-control no-cache`. It
  can stay where it is in `sync`: with no third-party call left in it, its only failure is
  an R2 write, the same dependency `publish` already has. One cheap `cp` a day also means a
  deleted or hand-edited `index.html` heals itself, which an on-push workflow would not do.
- The `Last updated` footer goes; the healthchecks badge in the page says whether the
  mirror is alive, and the README already explains `last-modified` for freshness.
- Two lines the current template lacks and the stated goal wants: `<meta name="description">`
  (what search results show) and `<link rel="canonical" href="https://ctan.ijosh.com/">`
  (so `/` and `/index.html` are not indexed as two pages).

Draft, to be edited rather than approved as is:

Follow-on edits: README step 7 becomes "upload the landing page", "Want your own?" step 2
says edit `site/index.html` instead of the template header, the `report` row says
"re-uploaded" instead of "re-rendered", CLAUDE.md's `page` gotcha shrinks to bucket root,
outside the prefix, `no-cache`, Transform Rule. `HOST` stays for the mirror URL; the page
carries the host literally, like the README does.

What is duplicated afterwards: the `tlmgr` URL and one descriptive sentence, in README and
page. The URL is the one constant in the project. That is the whole cost.

Alternative if the page must stay a rendered README: keep the renderer but move it to a
`page.yml` workflow on `push` to `main` with `paths: [README.md, site/template.html]` plus
`workflow_dispatch`, drop the token header and the footer, and add the same two `<meta>`
lines to the template. The daily run loses the API call; the machinery stays.

Neither version changes discoverability beyond the two `<meta>` lines. Search engines
reach the page through the README's link; if faster indexing matters, Search Console
verification is a dashboard step, not code.

### 2. `report` (kept by decision)

Thirty lines, the largest task in the file, to put six numbers on the summary page of a run
that succeeded. Nobody opens the summary of a green nightly; the failed-run email is the
signal, and every number in the table is available elsewhere:

| row | where it already is |
|---|---|
| Mirror, Fetched | the rsync `--stats` block, printed to the job log by `fetch` |
| Published | the `upload:` lines, which the log-capture gap makes unreliable either way |
| Storage | one `echo` in `guard` (below) |
| Signature, Read-back | constant text; `verify` and `smoke` passing is the statement |
| Landing page | gone with 1 |

Cutting it also removes what exists only to feed it: the `tee` in `fetch` and `publish`, the
two `set: [pipefail]` lines that exist to keep `tee` honest, `RUN` (if 3 goes too), the
`GITHUB_STEP_SUMMARY` heredoc, and the "log capture drops lines" and "`report` counts from
`RUN`" gotchas. CLAUDE.md notes a `report` with populated rows has never been seen, so
nothing observed is lost. Keep `--stats`: it is free and it is the log.

Make `guard` print the size every run, not only on failure:
`used=$(du -sm {{.STAGING}} | cut -f1); echo "staging: ${used} MiB (limit {{.LIMIT_MB}})"; test "$used" -le {{.LIMIT_MB}}`.
That is the one number worth a glance, and it lands in the log where the trend can be read
across runs.

### 3. `stale` and the deletion pass (kept by decision)

Twelve lines of `publish`/`stale`, a full bucket listing every day, a `test -s` tripwire, and
the longest gotcha in CLAUDE.md, to delete keys that the measurement above says appear at a
rate of tens a year. A stale container is invisible to `tlmgr`, which only fetches what the
tlpdb names; the only cost is storage, and package removals in TeX Live run to a few dozen a
year, well under 100 MB against a 3.2 GB margin. A platform retirement at a release rollover
is the big case, a few hundred files, still under the margin for years.

Cut the `aws s3 ls`, the `stale` task, the `xargs aws s3 rm` line and `RUN`. Keep one sentence
in CLAUDE.md: never `aws s3 sync --delete` on R2, with the one-line reason and the date.
The full diff logic stays in git history (121cb55) for the day a rollover removes thousands
of files; it is a one-off `comm` and `aws s3 rm`, not a daily step.

Caveat to decide on: `guard` measures staging, not the bucket, so bucket creep is not in the
number it prints. At tens of MB a year that is fine for a decade. If "exact mirror" is a goal
in itself, keep 3 and skip the rest of this section; it is correct as written.

### 4. The soft `guard` (applied, 196f082)

The 9 GB check exists to warn before the 10 GB check fails. Both warn through the same
email; the difference is when. tlnet has grown roughly 350 MB a year, so the soft guard fires
about two and a half years before the hard one, and the hard one already fails the run before
any upload, so the mirror is a day stale and nothing is billed. With `guard` printing its
number every run (2), the trend is visible on any day someone looks.

Cutting it removes `SOFT_MB`, a line of `sync`, and the last of the ordering commentary
("`ping` before the soft `guard`: one email, not two"). One `guard`, before `publish`, at
`HARD_MB`; rename it `LIMIT_MB` and drop the `vars:` indirection.

### 5. `size` (applied, d9d6a02)

A manual dry run whose exclude list duplicates `fetch`'s, so it drifts. `fetch` plus the
`guard` echo answers the same question in CI, and CLAUDE.md's "Verifying a Change" already
prefers that. Five lines, one less thing to keep in sync.

### 6. `check.yml` (kept by decision)

`task --dry sync` parses the YAML and renders the templates; undefined variables render
empty rather than fail, so it catches syntax errors and little else. Dependabot's PRs never
touch the Taskfile, human PRs are rare, and a broken Taskfile fails the next nightly with the
same email everything else uses. Thirteen lines and a second workflow for Dependabot to bump.
Cut it and the sentence in CONTRIBUTING that names it.

## Marginal, your call

- `verify`'s versioned-file test (`find ../archive -name '*.r[0-9]*.tar.xz'`). It tests our
  own exclude pattern; if the pattern breaks, the tree doubles to 13.6 GB and the hard `guard`
  on the next line refuses to publish anyway. Two lines for a clearer error message.
- `CONTRIBUTING.md`. Its ground rules are CLAUDE.md's hard constraints, copied. One line in the
  README ("ground rules for changes are in `CLAUDE.md`") does the job. If it stays, at least
  drop the "Checking a change" block, which is a third copy of CLAUDE.md's.
- `SECURITY.md`. GitHub shows the private-reporting link in the Security tab once the feature
  is on, and "what this mirror guarantees" restates the README's verify step. The one
  paragraph worth keeping is "uploads are not atomic, rerun `tlmgr`"; two sentences in the
  README's "How it works" carry it. Keeping the file costs nothing but a fourth copy of the
  verify story to update.
- `<!--HOST-->` substitution in the template. A fork edits the README's four URLs and the
  header links by hand anyway; the host in the title is a fifth edit, not a saving. Hardcode
  it, drop the `sed` expression.
- `max_concurrent_requests = 32`. The daily delta is tens of files; the default of 10 changes
  only the first full upload, from 80 s to a few minutes. One line.
- `aws --version` in `sync.yml`. Useful once, when a CLI bump changes behaviour. One line.
- The license badge. The other two badges say something the reader wants; this one repeats
  the last line of the README.

## Considered and kept

- The container check in `verify` (16 s, reads 6.8 GB). A tree caught between the tlpdb and
  its containers would give every `tlmgr` user checksum errors for a day; six lines is cheap
  for that.
- `gpgv` with the pinned fingerprint and `shasum -c` on the tlpdb. Each is one link of the
  chain (signature, sha512 file, tlpdb, container checksums) and none is redundant.
- `smoke`. One line, and it is what caught the 404 on 2026-08-26.
- `ping`. One line; the only thing that notices a run that never happened, which is how a
  60-day cron disable presents.
- The hard `guard` before `publish`. "Never bill" is a stated constraint, and it is what makes
  the versioned-file cut safe.
- `archive/` before the full sync in `publish`. The CLI walks the local tree in byte order, so
  `archive/` uploads before `install-tl*` and `tlpkg/` even in one sync; the split only
  matters for the last ~32 concurrent uploads. One line for a window that is small but real.
- `aws.config`. The multipart threshold has no environment-variable or flag form; the file is
  the only way to keep every upload a single Class A op.
- `--partial --delete --delete-excluded` in `fetch`. No-ops on a fresh runner, but they are
  what makes a local `task sync` behave like CI.
- `concurrency: sync`. A manual dispatch overlapping the cron is the one race the pipeline
  cannot reason about.
- SHA pins plus Dependabot. Two actions with R2 write credentials in their environment; tag
  pins would be shorter and the dependabot file could go, but this is the "not lazy about
  security" case.
- go-task itself. `make` is on every runner and every Mac, needs no setup action, no
  Dependabot entry, and `make -n sync` is the dry run. It would delete `setup-task` and
  most of `dependabot.yml`'s reason to exist. Not recommended against the stated preference
  and the rest of the dotfiles; noted because it is the largest single cut on the table.

## Where this lands

With 4 and 5 in and 1 as proposed:

```yaml
sync:
  cmds:
    - {task: fetch}
    - {task: verify}
    - {task: guard}
    - {task: publish}
    - {task: smoke}
    - {task: report}
    - {task: ping}
    - {task: page}
```

`guard` is one line that prints its number and fails past 10 GB. `page` is one `aws s3 cp`.
The only network endpoints are the CTAN master, R2, the public domain and healthchecks.io.
`Taskfile.yml` is about 165 lines; the template and its renderer are gone; CLAUDE.md loses
the soft-guard, `size`, rate-limit and render-check gotchas. The Taskfile comments that
restate a CLAUDE.md gotcha (the R2 ordering story, the sync ordering story) should still be
collapsed to one home each, next to the code.
