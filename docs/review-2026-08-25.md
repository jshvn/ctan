# Adversarial review, 2026-08-25

Scope: everything on `main` at 9805f19 (`Taskfile.yml`, both workflows, `aws.config`,
`site/template.html`, README, CONTRIBUTING, SECURITY, CLAUDE.md) plus the live domain.
Eight independent readers (line-by-line, removed-behaviour, cross-file, conventions,
reuse, simplification, efficiency, altitude) produced candidates; each one below was
re-checked by hand against the files, the staged tree in `staging/`, or a `curl` to
`ctan.ijosh.com`. Candidates that did not survive are listed at the end so they are not
re-raised. Line numbers refer to `main`.

## High

### 1. The edge caches the whole mirror for a day; CLAUDE.md says it does not

`curl -sI` on 2026-08-26 06:xx UTC, all `cf-cache-status: HIT`, all
`cache-control: max-age=86400`, query strings ignored (`latex.tar.xz?nocache=N` is a HIT),
and 404s are cached too:

| path | status | cache |
|---|---|---|
| `/systems/texlive/tlnet/archive/latex.tar.xz` | 200 | HIT |
| `/systems/texlive/tlnet/tlpkg/texlive.tlpdb.xz` | 200 | HIT |
| `/systems/texlive/tlnet/tlpkg/texlive.tlpdb.sha512` | 200 | HIT, age 3723 |
| `/` | 404 | HIT |
| `/LICENSE` | 404 | HIT |

That is a cache-everything rule (or equivalent) on the zone, not the default extension
list that CLAUDE.md line 57 relies on ("`.xz` is not in Cloudflare's default cache list, so
there is no stale-edge problem"). Because containers are overwritten in place under the same
key, any PoP that served `foo.tar.xz` in the last 24 h keeps serving the old bytes after a
revision bump while `texlive.tlpdb` (fresh or itself stale, per PoP) names the new checksum:
`tlmgr` reports checksum errors for up to a day, per package, per PoP. `smoke` reads
`texlive.tlpdb.sha512` through the same cache, so a same-day re-run compares staging against
yesterday's cached copy and fails although the upload was correct; the daily cron only passes
because 24 h + cron slack happens to exceed the TTL.

Fix, pick one:

- Cache Rule: bypass cache for `/systems/texlive/tlnet/*`. Every request becomes a Class B
  op (10 M/month free); this mirror's traffic is nowhere near that. `index.html` can stay
  cached. Zero code change.
- Keep the cache and add a purge to `publish` before `smoke`. Needs a Cloudflare API token,
  the zone id, a fifth secret and a new endpoint, which the hard constraints resist.

Bypass is the one that matches the repo's rules. Either way, update CLAUDE.md line 57.

### 2. `/` is a 404: the Transform Rule is not in effect, and `smoke` cannot tell

`/index.html` is live (200, `text/html`, uploaded 06:18 UTC); `/` is 404. URL rewrites run
before the cache lookup, so a working rule would make `/` a HIT on the `/index.html` key.
The 404 is now itself cached for a day (finding 1), so after fixing the rule, purge `/` or
wait. Nothing in the pipeline reads the landing page back; CLAUDE.md line 78 already lists
this as unverified. Cheapest check: one more line in `smoke`,
`curl -fsS -m 30 {{.SITE}}/ | grep -q 'class="markdown-heading"'`, with `SITE` derived from
`URL` (see finding 3 for the same split on the bucket side).

### 3. `publish` hardcodes the bucket name a second time

`Taskfile.yml:114` writes `s3://tlnet/index.html` while every other reference goes through
`BUCKET` (`s3://tlnet/systems/texlive/tlnet`). README line 67 tells forks to set only
`BUCKET` and `URL`. A fork with bucket `mymirror` syncs the whole mirror, then the `cp` fails
with NoSuchBucket/AccessDenied (the token is scoped to their bucket), `smoke` and `ping`
never run, and healthchecks alerts every day for a mirror that is fine. Split
`BUCKET_ROOT: s3://tlnet` and `BUCKET: '{{.BUCKET_ROOT}}/systems/texlive/tlnet'`, and cp to
`{{.BUCKET_ROOT}}/index.html`.

### 4. A cosmetic step gates the mirror update

`sync` runs `fetch -> verify -> guard -> page -> publish`. `page` is one `curl -fsS -m 30`
to `api.github.com/markdown/raw` plus a `grep` for `class="markdown-heading"`. A 5xx, a 403
rate limit, a 30 s stall, or GitHub changing its heading markup fails the run after the
6.8 GB download and before `publish`: the verified tree is thrown away, the mirror is a day
stale, and two alerts fire about a landing page. `page` has not yet run in Actions
(CLAUDE.md line 78), so its first exercise is a production sync.

Move it after `ping`, in the slot the soft `guard` already uses for "fail the job without an
outage": make `page` self-contained (render, then the `index.html` cp with the
`AWS_CONFIG_FILE` env), drop the cp from `publish`, and order
`... smoke -> ping -> page -> guard(soft)`. A broken render still emails; it never blocks
the mirror or trips healthchecks.

## Medium

### 5. No freshness check: a rolled-back tree passes `verify` and replaces a newer mirror

`fetch` reads `rsync://` in the clear. `verify` proves the tree is signed by the pinned key
and internally consistent; it does not prove it is newer than what is live. A MITM on the
rsync path, or a master that has itself been rolled back, can hand over last month's
validly signed tlnet, and `publish` will replace the current mirror with it (the tlpdb size
differs, so it uploads). `tlmgr` does not downgrade an existing install, but fresh installs
get old packages and the mirror regresses silently. One compare closes it: before `publish`,
take the highest `revision` in the staged tlpdb
(`awk '/^revision /{if($2>m)m=$2}END{print m}' texlive.tlpdb`, 80099 today) and the same
from the live `tlpkg/texlive.tlpdb.xz`, and fail if staged < live. Note the same plaintext
rsync path is also the runner's largest attack surface (rsync client CVEs against a
malicious server, on a host holding R2 write credentials); the bucket-scoped token is the
right mitigation and is already in place.

### 6. `--delete` runs before the new tlpdb lands

`aws s3 sync --delete` emits deletes interleaved with uploads in key order, and `archive/`
sorts before `tlpkg/`. On a day upstream drops a package, the second sync deletes
`archive/foo.tar.xz` and then uploads `tlpkg/texlive.tlpdb`; a runner killed between the two
(timeout, R2 5xx past the retry budget, Actions outage) leaves the old tlpdb naming a
container the bucket lacks until the next successful run. The desc on line 107 and
SECURITY.md line 11 promise otherwise. Split line 112 into `aws s3 sync` then
`aws s3 sync --delete`: one extra listing, about 18 Class A ops a day.

### 7. `texlive.tlpdb.xz` is never checked against `texlive.tlpdb`

`tlmgr` downloads `texlive.tlpdb.xz` first (`TLPDB.pm` line 331), decompresses it, and
verifies the result against `texlive.tlpdb.sha512`. `verify` checks only the plain file.
rsync transfers `tlpkg/` in name order (`texlive.tlpdb`, `.md5`, `.sha512`, `.sha512.asc`,
then `.xz`), so an upstream update landing during that window yields a new tlpdb with
yesterday's `.xz`, which passes `verify` and then fails every client until the next run.
Today's staging is consistent (checked). One line in `verify`:
`xz -dc texlive.tlpdb.xz | cmp - texlive.tlpdb`. `xz` is on ubuntu-latest and macOS; add
it to the dependency list.

### 8. A same-size revert is never re-uploaded

`aws s3 sync` uploads when size differs or local mtime is newer. If upstream re-points
`foo.tar.xz` at an older build of the same size (a revert), `rsync -t` gives it the old
mtime, the first sync skips it, and the bucket serves the newer bytes under a tlpdb that
names the old checksum. The header comment (line 27) assumes bumps are always newer;
reverts are rare but real. There is no cheap fix inside `aws s3 sync`; record it as a
known ceiling next to that comment, and note that finding 5's revision compare does not
catch it either.

### 9. Alert timing: 3 h grace against a 120-minute job and cron slack

Healthchecks: period 1 day, grace 3 h, measured from the last ping (~03:37). The job may
run 120 minutes and GitHub cron routinely starts 15 to 60 minutes late; a slow-but-alive
dante (rsync's `--timeout=300` only fires on a full stall) can push the ping past 06:37 and
raise a false down plus a recovery. The observed run is 7 minutes: `timeout-minutes: 30`
in `sync.yml` removes the false-alert case and cuts the alert latency of a wedged run by
90 minutes.

### 10. SECURITY.md and README overstate two guarantees

- "Read-back from the public URL is compared to what was uploaded" (SECURITY.md line 14):
  `smoke` compares one 144-byte file, through a cache (finding 1).
- "The previous good copy stays live" (line 11) and "A tree caught mid-update is never
  published" (README line 47): true of `verify`, not of `publish`. Containers are
  overwritten in place, so during the seconds between the archive sync and the tlpdb
  upload a client holding the old tlpdb gets checksum errors for every bumped package, and
  an interrupted `publish` leaves that mixed state until the next run (finding 6).

State the actual guarantee: a tlpdb is never published before the containers it names;
bumps can fail a client's checksum for the length of the tlpdb upload.

## Checked and dismissed

- Two `aws s3 sync` listings per run: ~36 Class A ops a day, 0.1 % of the allowance; the
  second listing is the price of the ordering invariant.
- Daily full 6.8 GB fetch: correct for a stateless runner; seeding from R2 destroys the
  mtimes `aws s3 sync` depends on, and `actions/cache` thrashes at this size.
- `--partial`, `--delete`, `--delete-excluded` are no-ops in CI and load-bearing locally.
- `-H "Authorization: ${GITHUB_TOKEN:+Bearer $GITHUB_TOKEN}"`: curl drops a header with an
  empty value; the trick works.
- Fingerprint pin from the mirror's own keyring: sound; a matching fingerprint is the same
  key, and vendoring the key would add a rotation chore without adding trust.
- `check.yml` on fork PRs: `task --dry` resolves `sh:` vars, so a PR could run a command
  on the runner, but the job has `contents: read` and no secrets.
- `aws.config`: no `multipart_chunksize` needed; the threshold keeps every object one
  PutObject.
